# AI calling cost audit — before implementation

Audit date: 2026-10-30. Scope: Express calling API, LiveKit worker and installed SDK source, question engine, knowledge/transfer, SIM router, transcripts, post-call extraction, analytics and regression tests. This report was written before implementation changes.

## Evidence and baseline

The supplied production call lasted 168 seconds: estimated USD 0.3616, 70,667 total tokens, audio input/output 7,190/1,213, text input/output 61,429/835, cached input 36,096. Input totals 68,619; output totals 2,048. Cached input is a subset of input, not an additional chargeable token count. The aggregate cache-hit ratio is 52.60%; cost/minute is USD 0.12914. Audio/text cost and cache savings cannot be independently reconstructed without the cached audio/text split and historical rates.

Both local API and worker environment files select `gpt-realtime`, voice `alloy`. The worker has a configurable model environment variable; dispatch metadata cannot select an arbitrary model. An API key exists, but no OpenAI admin/billing key was found. A read-only connection to the configured MongoDB failed with ECONNREFUSED. No production response events or billing export are available locally. The screenshot is supplied evidence, not an independently retrieved billing record. Consequently, exact attribution of those 61,429 text tokens and live before/after savings remain unverified.

## Architecture and lifecycle

- `aiCalling.service.js` owns authenticated, call-scoped tools, optimistic concurrency, disclosure, validated answers, branching, confirmation, retries, dispositions and result processing. `questionEngine.js` stores structured state; no LLM is needed to select the next question.
- `telephonyRouter.js` preserves paired-phone SIM and SIP/fallback providers. The separate `agent-worker/src/agent.js` bridges LiveKit PCM audio to OpenAI Realtime over the installed plugin. PSTN waits for active SIP; browser sessions currently connect Realtime before the participant arrives.
- `leadContext.js` builds the system prompt with configured language, identity, objective, recording rules and all question labels/text. The worker adds disclosure and extensive rules again. Approved versioned business knowledge and human transfer rules are appended by the API.
- Answers are stored immediately, validated server-side, and retained independently from model history. Bulk answers, clarification, interruptions, opt-out, callbacks, transfer, language selection and critical confirmations already exist; they should be extended, not replaced.
- Transcripts stream to the API with atomic item-ID deduplication. Existing retention is 300 transcript items, 4,000 characters per item and 90 days. Model-context compaction must never delete CRM transcripts or answers.

## Findings

1. **Confirmed prefix mutation on every tool result.** `nextFrom()` calls `agent.updateInstructions(withCurrentStep(baseInstructions, pending))`. The entire instruction prefix changes for each question, clarification and confirmation. This is not append-only history and impairs cache reuse. The current step is also returned in the tool output.
2. **Confirmed redundant instruction content.** Backend and worker both describe short responses, answer validation, multi-answer handling, no fabrication, interruptions and retries. The backend includes unnecessary examples. Lead name/city appear early, before reusable campaign instructions/knowledge, reducing reuse across leads. The full lead database, notes and CRM history are not repeatedly sent to OpenAI. `leadContext` and optional `leadNotes` are returned in the API payload but the worker does not inject them again.
3. **Cumulative inputs explain the apparent text amplification.** Realtime bills every generated response against its retained input, including instructions, tool schemas, prior tool calls/results and assistant history. A spoken turn can involve a tool-only response and a follow-up spoken response. The source does not manually resend the whole CRM transcript on ordinary turns. Installed LiveKit `updateChatCtx` computes item differences; reconnects restore conversation. There is no evidence that 61,429 represents unique text or a single huge initial prompt. Aggregate SDK usage cannot attribute exact token amounts by context component.
4. **No explicit response output cap.** Installed plugin defaults `maxResponseOutputTokens` to `inf`. Long spoken replies and finish-call notes can consume avoidable output. Use a configurable moderate cap that permits structured tools; test incomplete responses.
5. **No application context budget/compaction.** Existing history relies on provider defaults. Frequent deletion would harm caching. Introduce thresholded compaction at safe completed-turn boundaries, keep complete recent exchanges, preserve exact structured answers and current action, and archive transcripts before mutation. Never compact every turn or while tool calls are in flight.
6. **Usage loses response granularity.** `billingUsage.js` correctly treats SDK usage as cumulative, preserves model metadata and avoids adding snapshots. Only final aggregate usage is stored. Installed SDK exposes `metrics_collected` with response ID, modality tokens, cache modality split, TTFT and cancellation; capture it once per response without adding it to session totals.
7. **Audio configuration is mostly sound.** Installed SDK uses mono PCM16 at 24 kHz. Server VAD is threshold 0.5, prefix 500 ms, silence 1,000 ms, automatic responses and interruption enabled; semantic VAD is configurable. No manual empty audio commits were found. Separate contextual ASR (`gpt-transcribe`) supports English spelling/code switching and must remain for validation gates. Existing VAD hardcodes interruption on even when campaign barge-in is off. Keep spelling pauses and audio quality; do not disable ASR for a speculative saving.
8. **Shutdown depends on room deletion.** `/end` is once-only and follows goodbye playback, but does not explicitly close `AgentSession` before reporting usage. Its max-duration timer and watchdog can remain until worker cleanup. Explicitly stop capture/generation and close the session, then flush final transcript/usage; preserve once-only reporting and SIM hangup.
9. **Retries already have safeguards.** Confirmation and no-response API retries reuse request IDs; answer gate blocks duplicate responses from one speech turn. Fatal provider errors are classified. Preserve these behaviors. Observe cancelled/retried provider responses because they can still consume usage.
10. **Cost arithmetic already has meaningful protections.** `callCost.js` prices each model separately using configurable rate cards, discounted cached modalities, snapshot-family resolution and ambiguity checks; provider totals take precedence. Unknown model/cache splits remain unpriced. Existing rates are historical defaults, not proof of current account pricing. UI explicitly labels estimates, excludes tests from production totals and separates carrier/platform costs. Missing features: per-response usage/cost, per-call cache ratio, cached savings, average output length, and evidence-based comparisons.
11. **Costs outside the displayed estimate.** Separate input ASR and `callIntelligence.service.js` Chat Completions extraction are not included in Realtime model totals. Extraction is transcript-version idempotent, has bounded output and queued retries, but discards provider usage. It uses system/user messages; do not add Realtime cache parameters or rewrite requests blindly. Preserve usage separately before claiming an all-inclusive call bill.

## Official API constraints

[OpenAI Realtime cost guidance](https://developers.openai.com/api/docs/guides/voice-latency-cost?voice-api=realtime) documents best-effort automatic prefix caching, instruction/tool changes invalidating reuse, retention-ratio truncation and item deletion/summary approaches. The installed LiveKit plugin does not expose a truncation constructor option; use its supported chat-context API for application compaction rather than inventing options or editing node_modules. No `prompt_cache_key` or retention parameter will be added to Realtime requests.

[OpenAI pricing](https://developers.openai.com/api/docs/pricing) currently lists newer Realtime families; they require exact independent rate cards. Do not substitute a newer model or infer its rates from a name prefix. `gpt-realtime-mini` remains a candidate selected through the existing environment setting, with no production model switch until identical live qualification tests pass. Chained ASR/text/TTS or GPT-Live would change the architecture and latency profile; evaluate separately instead of rebuilding this working system.

## Implementation and validation plan

Freeze standing instructions; persist next steps in normal tool results and an initial checkpoint. Put shared instructions/knowledge before per-lead data. Apply the supplied concise base behavior while retaining compliance, validation, language and transfer requirements. Add response telemetry, cache diagnostics, configurable output/context limits, safe structured checkpoints and explicit session close. Extend the current dashboard with measured usage and labeled cost estimates; comparisons must require real compatible cohorts and never infer monthly volume. Add meaningful regression tests for workflow, safe compaction, duplicate metrics, cache accounting, failed/reconnected sessions and cleanup. Live call and invoice results remain a separate acceptance gate; no synthetic token counts or savings will be represented as provider measurements.
